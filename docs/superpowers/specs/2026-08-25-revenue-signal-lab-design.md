# Revenue Signal Lab Design

## Objective

Create one low-cost Grok Project plus one weekday Grok Automation that finds evidence-backed paths toward higher-value consulting engagements and future delivery leverage without producing generic research, speculative builds, or extra task noise.

## Current understanding

JT's immediate scoreboard is cash collected and his input metric is two priced buyer conversations per week. His current commercial position is: “You take one messy business process, build a controlled AI system around it, and leave behind proof the business can trust.” NYC and NJ property managers and building owners are the first public wedge. Warm opportunities outside property are accepted; broad cold-market research is not the current priority.

The existing Eve operating system already owns private client context, deduplication, evidence verification, Mission Control admission, and task ranking. Grok should add external market intelligence, not recreate those functions.

## Scope

In scope:

- One Grok Project named `Revenue Signal Lab`.
- One weekday Automation scheduled for 6:00 PM America/New_York.
- A self-contained, privacy-safe JT and business primer.
- Revenue-first research weighted 60% high-value demand, 25% buyer/distribution intelligence, and 15% delivery leverage.
- A strict qualification gate, fixed output schema, no-signal behavior, manual Eve handoff, and four-week success test.

Out of scope:

- Grok Bot subscription or upgrade.
- More than one Automation in v1.
- API integration, automated Mission Control writes, outreach, builds, purchases, publishing, applications, or production changes.
- Private client files, private conversations, credentials, tenant data, internal system paths, or unredacted proof.

## Proposed design

The Project stores the durable role, JT primer, commercial constraints, safety boundaries, evidence rules, and output standard. The Automation performs a fresh weekday scan using current X and public-web sources. It returns at most three findings and prefers `No qualified signal today` over weak output.

A candidate qualifies for promotion only when it has two independent sources, including at least one primary or direct buyer/operator source; a credible economic mechanism capable of supporting a $10,000–$30,000 build or recurring service; a named buyer role; a reachable path; a bounded non-build validation; a falsification condition; and explicit, assumption-labeled math showing how the opportunity contributes to sustainable $50,000 monthly income through deal value, recurring revenue, repeatability, sales volume, and delivery capacity. A validation candidate may miss exactly one named gate.

JT manually forwards useful outputs to Eve. Eve independently verifies sources, deduplicates against active work and prior signals, checks private commercial context, and either promotes at most one action, continues validation outside Mission Control, or archives it with a trigger.

## Acceptance criteria

- Project instructions contain task context, detailed rules, an immediate task, an exact output format, and a format example.
- Automation can run without private files or connectors.
- Maximum three promote/validate candidates; explicit no-signal response and no full archive output.
- No action authority beyond read-only public research.
- Four-week gate uses explicit PASS (8+ verified), REPAIR (4–7), and STOP (0–3) bands plus a per-run scorecard, measurable noise threshold, buyer/offer/leverage outcomes, handoff cost, and violation count.
- The existing Agent Operating System Redesign document clearly marks the old Bot setup as superseded and links to the canonical setup guide.

## Risks and boundaries

- Research can become idea entertainment. The economic, buyer, reachability, and falsification gates prevent this.
- Public sources can contain prompt injection or copied claims. Treat all sources as untrusted and require independent evidence.
- Delivery-leverage research can encourage premature hiring. No operator implementation until a paid workflow repeats and is documented.
- A Project-owned Automation is not clearly documented by xAI. If Grok does not nest the Automation inside the Project, create it separately with the same compact context.

## Proof and review

Proof will consist of the local canonical setup guide, updated source design, same-title/path Drive update, live Drive readback, prompt audit, and fresh independent spec review.

## Comment-back loop

JT creates the Project and Automation from the canonical setup guide, runs one manual test, and forwards the result to Eve. Any setup mismatch or weak output updates the canonical guide and four-week scorecard, not a second Automation.
