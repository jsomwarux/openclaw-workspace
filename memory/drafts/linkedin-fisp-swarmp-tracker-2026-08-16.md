A property manager can have the last FISP report, the next filing date, and the facade tracker all in one place and still miss the repair risk.

A tracker that just adds five years to the last filing is tracking arithmetic.

Local Law 49 changes the FISP inspection framework from the traditional five-year cycle to a DOB rule-based interval between six and twelve years. DOB's current public guidance still describes five-year filings, so this is exactly the kind of transition where a spreadsheet can look current while the rule logic underneath it is stale.

The filing date is only one part of the risk.

The control point is the classification on the last report.

Every SWARMP condition should become its own tracked item:

- condition
- source report
- recommended repair date
- repair owner
- permit or contractor dependency
- QEWI follow-up
- proof that the condition was corrected

Otherwise it stays buried as a line in a report nobody reopens until the next cycle.

That is where the silent failure happens.

A prior-cycle SWARMP condition that is still open at the next inspection can turn into an UNSAFE path. At that point the workflow is no longer just "file the next report." It is protection, repair timing, DOB status, owner review, and money.

The workflow I would build starts with the last accepted FISP report.

It pulls every SWARMP item into a repair queue with a named owner. It keeps the cycle date separate from the repair date. It requires a human to confirm the building's block, sub-cycle, DOB status, and rule basis before anything gets rescheduled.

UNSAFE is a separate lane. Anything touching legal timing, public protection, or owner spend stays in review.

Pull the last FISP report. Find every SWARMP condition. Then ask what date your system thinks each repair is due.
